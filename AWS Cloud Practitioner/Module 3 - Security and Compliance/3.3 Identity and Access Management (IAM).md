# 3.3 Identity and Access Management (IAM)

**IAM** controls **who** can sign in (**authentication**) and **what they're allowed to do** (**authorisation**). It's **global** (not tied to a Region) and **free**.

## The building blocks

| Part | What it is | Example |
|---|---|---|
| **Root user** | The email that created the account. It can do everything | Only for a few account jobs |
| **IAM user** | One person or app, with long-term credentials | `juan` |
| **IAM group** | A collection of users that share permissions | `Developers`, `Admins` |
| **IAM role** | A set of permissions that someone or something **takes on temporarily** | An EC2 server that needs to read S3 |
| **Policy** | A JSON document listing what's allowed or denied | "Allow reading S3 buckets" |

## A policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

- **Effect:** Allow or Deny
- **Action:** what can be done (`s3:GetObject` means read a file from S3)
- **Resource:** what it can be done to
- **An explicit Deny always wins** over an Allow. Anything not allowed is denied by default.

## Best practices (heavily tested)

1. **Lock away the root user:** turn on MFA, and don't use it for everyday work or create access keys for it.
2. **Least privilege:** give only the permissions needed, and nothing more.
3. **Use groups** to give permissions, instead of attaching them to each user.
4. **Turn on MFA** for everyone.
5. **Use roles for apps and AWS services** (temporary credentials), never access keys stored in code.
6. **Use a strong password policy**, and rotate access keys.
7. Review access with the **IAM credential report** and **IAM Access Analyzer**.
8. For people, **IAM Identity Center** (single sign-on) is AWS's recommended way to manage access across accounts.

## Tasks only the root user can do (examples)

- Change the account's email, name or root password
- Close the AWS account
- Change the **AWS Support plan**
- Restore IAM permissions if the only administrator loses access
- Register as a seller in the Reserved Instance Marketplace

## 3.3.4 The three ways to access AWS

| Way | What it is | Signs in with |
|---|---|---|
| **AWS Management Console** | The website | Username, password and MFA |
| **AWS CLI** (command line interface) | Commands typed in a terminal, like `aws s3 ls` | Access keys, or single sign-on |
| **AWS SDKs** | Code libraries for programming languages (such as JavaScript and Python) | Access keys or roles |

**AWS CloudShell** is a terminal *inside* the Console with the CLI already set up, using your console sign-in. There are no keys to manage, and it's free.

## Roles: why they matter

- A role has **no password or long-term keys**. Whoever takes on ("assumes") the role gets **temporary credentials** that expire.
- Common uses:
  - An **EC2 instance** reading from S3 (an **instance profile**)
  - A **Lambda function** writing to DynamoDB
  - **Cross-account access** (a user in account A working in account B)
  - **Federation**: signing in with Google, Microsoft or a company login
- A role has two policies: a **trust policy** (*who* can assume it) and a **permissions policy** (*what* it can do).

## Exam tips (3.3.2)

- "An application on EC2 needs to access S3 securely" means an **IAM role**, never access keys on the server.
- "Give the minimum permissions needed" means **least privilege**.
- "Manage permissions for many users at once" means **IAM groups**.
- "Extra sign-in security" means **MFA**.
- "Which task needs the root user?" Changing the support plan, closing the account, or changing account settings.
