# 4.5 AWS Global Infrastructure

| Part | What it is | Why it matters |
|---|---|---|
| **Region** | A separate **geographic area** (like London, `eu-west-2`), with **at least 3 Availability Zones** | Data stays in the Region you choose (**compliance**), and you can be close to users (**latency**) |
| **Availability Zone (AZ)** | **One or more data centres** with separate power, cooling and networking, a few miles from the others in the same Region | Run in **2 or more AZs** for **high availability**: if one AZ fails, the others keep going |
| **Edge location** | A site in a big city used to **cache content** close to users | Used by **CloudFront** (content delivery), **Route 53** (DNS) and **Global Accelerator** |
| **Local Zone** | AWS infrastructure placed **in a big city**, close to users | Very low latency for things like video editing and gaming |
| **Wavelength Zone** | AWS infrastructure inside **5G mobile networks** | Very low latency for mobile apps |
| **AWS Outposts** | AWS hardware installed **in your own data centre** | Hybrid cloud: run AWS services on-premises |

## Choosing a Region: four factors

1. **Compliance:** laws may require data to stay in a country.
2. **Latency:** closer to users means faster.
3. **Service availability:** not every service is in every Region.
4. **Pricing:** prices differ between Regions.

## Global and regional services

- **Global:** IAM, Route 53, CloudFront, WAF (for CloudFront), and billing.
- **Regional:** almost everything else: EC2, RDS, Lambda, VPC, and **S3 buckets**. S3 appears global in the console, but each bucket lives in one Region.

## Exam tips (4.5.2)

- "**High availability** within a Region" means **several Availability Zones**.
- "**Disaster recovery** from a whole Region failing" means **another Region**.
- "Lower latency for users around the world for static content" means **CloudFront** with **edge locations**.
- "AWS services **in my own data centre**" means **Outposts**.

## Lab 4.5.3.1: S3 buckets in two Regions

💰 **Free:** empty buckets cost nothing.

1. Open **S3** → **Create bucket**.
2. **Bucket name:** something globally unique, like `juan-lab-london-2026`. **Region:** **Europe (London) eu-west-2**. Leave **Block all public access** on → **Create bucket**.
3. Create a second one: `juan-lab-virginia-2026` in **US East (N. Virginia) us-east-1**.
4. In the bucket list, look at the **AWS Region** column: each bucket lives in **its own Region**, even though S3 shows them all together.
5. Upload a small file to each, and open its **Properties** to see its Region and address.

**Why it matters:** bucket names are **global** (nobody else can use yours), but the **data stays in the Region you chose**.

**🧹 Clean up:** empty and delete both buckets, unless you're using them for **Cross-Region Replication** in Lab 4.9.4.
